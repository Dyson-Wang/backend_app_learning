# 消息队列

## 三种投递语义

| 语义 | 含义 | 代价 |
|---|---|---|
| 至多一次 | 可能丢，绝不重 | 业务丢消息 |
| 至少一次 | 绝不丢，可能重 | 消费端必须幂等（业界默认） |
| 恰好一次 | 不丢不重 | 需要事务 / 幂等 + 去重配合，代价最高，别轻信「框架保证」 |

**结论**：生产上按「至少一次」设计，把正确性交给消费端幂等，而不是指望 MQ 恰好一次。对应 `advanced/B02`、`D01`。

## 消费端四件套

1. **幂等**：用业务唯一键（订单号 / 消息 ID）做去重表，唯一索引是最省事的兜底
2. **显式 ACK**：处理成功后才确认；处理失败要区分可重试错误与永久错误
3. **重试与退避**：指数退避 + 抖动，限制最大次数，避免 `advanced/F02` 的重试风暴
4. **死信队列**：超过重试次数进 DLQ，附带原始消息、失败原因、重试次数，并留人工重放入口

## 顺序性

全局有序和高吞吐是冲突的。常见做法是**分区有序**：按业务键（如 `account_id`）哈希到同一分区，分区内单消费者串行处理。跨分区的全局顺序需要额外协调，通常说明业务设计该改。对应 `advanced/D03`。

## 事务消息 / Outbox

「写 DB 成功但发消息失败」是经典不一致。本地消息表（outbox）在同一事务里写业务数据和待发消息，由独立进程轮询投递，再用幂等消费兜底。示例表见 `sql-and-postgres/schema.sql` 的 `outbox`。

## 积压

积压先看消费速率与分区数，不要盲目加消费者（分区数决定并行上限）；同时要有降级开关和跳过非关键消息的能力。对应 `advanced/F03`。

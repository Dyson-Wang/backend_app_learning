# 一个请求的完整链路

后端所有「场景」都挂在这条链路上。先记住链路，再换语言实现。

```
Client
  -> DNS / TLS 终止
  -> Nginx 反向代理（限流、超时、请求体大小、access log、trace id 注入）
  -> 应用服务（路由、鉴权、参数校验、业务逻辑、事务边界）
       -> PostgreSQL（连接池、事务、索引、锁）
       -> Redis（缓存、分布式锁、限流计数）
       -> 消息队列（异步任务、削峰、重试、死信）
  -> 响应（统一错误码、分页元数据、trace id 回传）
  -> 旁路：结构化日志 / 指标 / 链路追踪 / 告警
```

## 每一段的经典故障

| 位置 | 故障 | 对应场景编号 |
|---|---|---|
| 网关 | 突发流量打穿应用 | A01 限流、A05 背压 |
| 应用 → 依赖 | 下游慢导致线程池 / 连接池耗尽 | A02 超时重试、C01 连接池、F01 慢查询 |
| 应用 → 依赖 | 重试放大，把小故障变成雪崩 | A03 熔断、F02 重试风暴 |
| 数据库 | 事务隔离级别理解错，出现超卖 / 脏读 | B01 事务、B03 分布式锁、B04 竞态 |
| 缓存 | 穿透 / 击穿 / 雪崩、缓存与 DB 不一致 | C04、C05 |
| 消息队列 | 至少一次投递带来的重复消费 | B02 幂等、D01、D02 |
| 客户端重试 | 网络抖动导致同一请求提交多次 | B02 幂等 |
| 发布 / 扩缩容 | 进程被杀时正在处理的请求丢失 | A04 优雅关闭 |
| 全链路 | 出问题时查不到是哪一步慢 | E04 可观测性 |

## 两条贯穿始终的原则

1. **任何跨进程调用都必须有超时和取消**：没有超时的重试等于给故障加杠杆。
2. **任何可能被重复执行的写操作都必须幂等**：至少一次投递 + 客户端重试是常态，不是异常。

这两条在 5 门语言里的实现方式完全不同（Go 的 `context`、Node 的 `AbortSignal`、Python 的 `asyncio.timeout`、Java 的 `CompletableFuture.orTimeout`、Rust 的 `tokio::time::timeout`），正是 `99-cross-language/` 要对照的第一个主题。

# Redis 与缓存

## 三大经典问题（别再背混了）

| 问题 | 触发条件 | 后果 | 解法 |
|---|---|---|---|
| 穿透 | 查询**根本不存在**的 key（恶意 ID / 爬虫） | 每次都打到 DB | 布隆过滤器 / 缓存空值（短 TTL）/ 参数校验 |
| 击穿 | **单个热点 key** 恰好过期，大量并发同时回源 | 瞬间压垮 DB | 互斥锁只放一个回源 / 逻辑过期 + 后台续期 / 热点永不过期 |
| 雪崩 | **大批 key 同一时刻过期** 或 Redis 整体不可用 | DB 流量尖峰 | TTL 加随机抖动 / 多级缓存 / 熔断降级 |

## 双写一致性

没有银弹，只有取舍。主流方案是 **Cache-Aside + 延迟双删**：

1. 读：先读缓存，miss 则读 DB 并回填
2. 写：先更新 DB，再删缓存（**不是更新缓存**）
3. 为兜住「读请求在写请求之间把旧值回填」的竞态，延迟一小段时间再删一次
4. 强一致要求高的场景，改用事务消息 / CDC（如监听 binlog）同步缓存

为什么是删缓存而不是更新缓存：两个并发写操作若都去 `SET` 缓存，后完成的可能先写，导致缓存里是旧值。删除是幂等的，更安全。

## 分布式锁

- 加锁：`SET key value NX PX ttl`，value 必须是随机 token
- 解锁：Lua 脚本先比较 token 再 `DEL`，**不能**直接 `DEL`（会误删别人续期后的锁）
- 必须设 TTL，且要评估业务执行时间超过 TTL 的情况（看门狗续期 / 改用数据库乐观锁）
- 单机 Redis 的锁在主从切换时可能失效；强一致场景用 Redlock 或直接改用数据库 / etcd

对应 `advanced/B03`。

## 限流计数

`INCR` + `EXPIRE`（固定窗口，有边界突刺）、`ZSET` 滑动窗口、或 Lua 脚本实现令牌桶。对应 `advanced/A01`。注意 Redis 版的原子性靠 Lua，应用内多实例各自限流是分布式限流的前提。
